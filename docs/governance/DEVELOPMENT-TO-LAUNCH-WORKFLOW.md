## 2. 职责与执行纪律

| 角色 | 责任 |
| --- | --- |
| 总控 | 继承成果、排程、核授权范围和回执、组织差额及权威记录；不代执行Docker、DB/SQL、Git、部署或真实环境操作 |
| 唯一原执行者 | 沿既有聊天/工作区完成已授权工作、定向验证、保全失败与证据，准确报告实际结果 |
| 原另一组 | 沿既有分工；暂停不因本文或阶段完成自动解除 |
| 业务、安全、合规、运营验收人 | 在相应阶段由所有者指定；缺人就登记未就绪，不由开发/总控代签 |
| 所有者 | 决定首发范围，裁定新增权限/结构/样本/发布/暂停解除，完成相应正式签收 |

普通已授权步骤连续完成。新增范围集中列清具体动作、影响、验收和恢复方式，不重复请批同一业务。技术静审、原生审批、阶段验收和部署授权各有边界，不能相互替代。

## 4. 任务卡固定格式

每项任务使用以下字段，可直接附在既有执行单或原交付记录中，不另建状态系统：

| 字段 | 填写要求 |
| --- | --- |
| ID/阶段/业务流程 | 沿原矩阵ID或既有任务ID；新增任务说明来源 |
| 继承依据/必要差额 | 引原实现、测试、回执；明确只补什么，避免重复工作 |
| 负责人/验收人 | 实施和签收分开；未指定者标待指定 |
| 授权与前置 | 来源、范围、环境、次数、暂停与原生审批条件 |
| 操作与验收 | 具体步骤、业务对象、预期结果、失败停点 |
| 实际结果 | 未开始/执行中/条件阻塞/暂停/待裁定/完成；验收另标PASS、LIMITED、FAIL或UNKNOWN，二者不混用 |
| 证据与版本 | 源码、依赖、制品、运行身份、测试层次及回执路径；敏感信息不公开 |
| 剩余与下一步 | 准确差额、责任人、依赖、必要裁定和排期变化 |

历史实现、历史测试、离线验证、实际发布、当前真实验收、源码归并及治理签收分开记录。空集只能证明实际空集及相应结构范围，接口200/CI成功不能代替业务闭环。

## 5. 阶段放行记录模板

每次阶段出口在原交付目录形成记录，并向三权威文件追加对应结果/链接：

```text
阶段/里程碑：
范围与固定候选版本：
入口条件与授权依据：
完成任务及证据：
未完成项、影响、责任人及处置：
测试层次与未覆盖项：
技术验收结论/验收人/日期：
治理签收状态/签收人/日期：
结论：通过 / 限定通过 / 未通过
下一阶段前置及尚缺授权：
```

限定通过必须准确写范围，不代表全阶段全部义务闭环；存在硬前置未满足时不得据此启动下一阶段。业务、安全及所有者签名只能由相应责任人作出。

## 6. 变更、发布与恢复

任务先引用已有成果，再做最小差额与有意义的定向测试。已经定位且授权涵盖的缺陷可连续处理，不等全模块走查结束；已通过项仅因相关变更、证据冲突或失效而定向复验。

发布前固定源码/依赖/制品/配置/验收及恢复清单，取得对应环境、动作与次数授权；回执记录实际运行身份。后续任何新发布不能复用已消耗许可，不能把候选封存当部署批准。资金数据的恢复须考虑已发生交易，不能只用代码回滚代替账务恢复。

原生拒绝/超时不换通道或盲重试；错误未知保持未知，不猜凭据、权限或平台根因。范围改变时追加影响说明、授权差额、需要重验的路径及排期变化。

## 7. 持续跟进与自动化边界

每次实质进展回报：完成内容、版本与证据、剩余、阻塞及责任人、下一动作、排期变化。没有实质变化的监控安静，不把空闲等待称为持续开发，不编完成百分比或日期。

本文没有安装后台监听器、节点执行器、自动发布或自动放行。现有专用监控沿原ID和边界运行，不重复创建。将来若获准增加静态字段/链接/完整性检查，也不能自动解除冻结或代人签收。适用P节点约定仅在真实可信执行上下文满足时执行，不能从本文生成伪上下文。
